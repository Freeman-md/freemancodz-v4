## Mandatory approval checkpoints

Use the architecture table already present in the contract template, plus task/PR handoff fields; do not create another decision register. For each relevant task record `NONE`, `EXISTING APPROVED ADR` or `NEW/REVISED ADR REQUIRED`, with reasons, ARC/STD/ADR references, exact owner evidence/version/scope, affected/blocked tasks, propagation and resumption status.

1. **Authoring, before execution approval:** the orchestrator tests the proposed outcome and implementation against current contracts. `NONE` means no new decision, not exemption from rules. Existing ADR reuse must match its actual scope. A new rule, exception or material deviation gets a **PROPOSED — AWAITING APPROVAL** ADR and a concise owner brief before dependent implementation. Keep draft criteria unchecked.
2. **Planning, before dispatch or resume:** independently check task-to-decision mapping, accepted status and owner evidence, available prerequisites, contract version and prior findings. A frozen active contract or “Run” instruction cannot approve a newly discovered architecture change. Retain the same PR and review budget on resume.
3. **Executor, before edits and on discovery:** independently assess actual dependencies, ownership, trust/transaction boundaries and exceptions. A new consequential choice stops its named dependent tasks immediately. Send the orchestrator the evidence, smallest recommendation, alternatives/trade-offs, rule/ADR IDs and exact blocked work; unrelated authorized work may continue only if it does not constrain the pending decision.
4. **Owner decision and propagation:** only explicit `APPROVE`, `REVISE` or `REJECT` resolves the brief. Record evidence, date, reviewed version/hash, conditions and task scope. After approval, align the accepted ADR, affected contracts, milestone/task instructions and verification requirements; obtain the executor's acknowledgement before recording resumption. Future implementation/enforcement work stays scheduled until verified. Revision/rejection returns affected work to planning. Tests, silence, a review PASS or an “accepted” label cannot substitute.
5. **Independent review and merge handoff:** the reviewer verifies actual implementation against accepted scope and the propagation sequence. Unresolved required approval or inconsistent handoff prevents PASS/READY. The orchestrator verifies the returned review and current evidence before the existing final decision. Architecture approval and implementation readiness do not grant owner merge, hosted-change or release authorization.

[APPROVAL-001](setup/APPROVALS.md#approval-001--d1-and-d2-approved) is reusable evidence for D1's authority and D2's narrow injected type/inert-error boundary. It does not approve provider-client-file error imports, private Meeting helpers, arbitrary exceptions or a future milestone. The [Task 04 propagation review](setup/REVIEWS.md#task-04--acceptance-propagation-pass) and [Task 05 handoff](ENGINEERING_SETUP_STATUS.md#task-05-execution-handoff-authorised-after-propagation-review) demonstrate real approval, propagation, executor acknowledgement and subsequent authorized work. ## Freeze the full review scope

At handoff, pause edits and identify the repository, milestone/version, exact base and target commits, PR branch/base and the actual diff direction. Use the recorded base-to-target diff; if the PR uses a merge base, record that SHA too. GitHub PR checks commonly execute a test-merge SHA: record both PR head and tested merge SHA plus its parent/base relationship. A passing check on a different head/base cannot approve the current PR.

The quality JSON's safe input digest is deliberately narrower than a full review. It excludes operational receipts, some local skills and Git index/mode state. Attach a separate review snapshot to the existing handoff, outside the scanned checkout or in the authorized PR record. This is an evidence format/procedure, not a new mandatory runner:

| Field             | Binding requirement                                                                                                                                                                                                                                                                |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Contract          | Milestone ID/version, complete frozen approved contract and SHA-256; approval/conditions and acceptance checklist. Only inspect the current active file during an actual authorized workflow; isolated trials use their own draft.                                                 |
| Revisions         | Exact base, target HEAD and relevant merge-base/test-merge IDs, plus inspected repository identity. Do not invent commits for manifest-only fixtures.                                                                                                                              |
| Path inventory    | Base/target tree metadata; index entries including mode, blob ID and conflict stage; staged and unstaged changed path/status lists; relevant untracked paths. Record additions, deletions, renames and executable-mode changes.                                                    |
| Safe content      | For every reviewed regular file, base/target and current index/worktree content hashes or absent markers, plus exact safe patch/hash. Include changed hooks, local skills, CI, approval/baseline changes and other review-relevant paths even when quality identity excludes them. |
| Exclusions        | Owner changes excluded from the candidate, generated/dependency outputs and any prohibited/unknown paths, with reasons. No excluded required change can silently pass.                                                                                                             |
| Evidence / review | Report/log/run hashes and locations, exact commands/exits/counts, provenance and scope; reviewer context, reviewed snapshot digest, verdict/findings and actual PR review link when applicable.                                                                                    |

Inspect **path metadata first**, using bounded Git metadata such as `git diff --name-status -z`, `git diff --cached --name-status -z`, `git ls-files --stage -z` and `git ls-files --others --exclude-standard -z`. Do not run an unrestricted content diff/archive/search. Reject secret-bearing names, credentials/private material, unknown content types, path traversal and symlink components before any file/blob read. Explicitly select known safe authored paths, then obtain their base/index/worktree content and diff. A secret or unsupported required input yields BLOCKED with metadata-only explanation and a safe-substitute request, never a secret hash or copied content. Locally ignored build/dependency outputs are not reviewed authored changes; an ignored required contract is included explicitly under its authorized workflow.

Serialize the selected manifest and patch deterministically (sorted repository-relative paths, explicit null for absence, modes retained), hash the exact bytes and give the reviewer the files and method. Record inventory exclusions so completeness can be checked. The reviewer recomputes the identity before review and before verdict. Index and worktree are separate: staged good content cannot conceal bad unstaged changes, nor can clean worktree content replace a bad staged blob. A new relevant untracked file, mode change, base advancement or post-review edit invalidates the affected handoff; freeze again, run applicable checks and obtain a fresh verdict. Never reset review count to hide this.

An unsigned local JSON/manifest is not an attestation. Independently inspect actual execution logs, tool observations or trusted hosted run provenance. A producer's assertions and a digest alone cannot prove checks ran or owner approval exists. A changed file outside quality's scope still requires full-diff review; a changed quality input requires a new matching canonical report, not relabeling an old report.

## Review loop and existing status mapping

Delegate a separate context and explicitly invoke [the existing local review skill](../../.agents/skills/independent-review/SKILL.md), supplying the full frozen handoff. For real milestones use the global review template, same PR posting and review-history recovery. The author cannot approve their own work. | Repository outcome | Existing reviewer wrapper / workflow result                                                                                                              | Next action                                                                                                                                  |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| PASS               | `APPROVE`; supports `APPROVED` / READY only after all current milestone obligations and checks match                                                     | Copy the milestone-specific Manual Checkpoint unchecked; owner separately decides merge.                                                     |
| CHANGES REQUIRED   | `REQUEST_CHANGES`; intermediate, never completion                                                                                                        | Return stable findings to executor, fix the same scope/branch/PR, record dispositions and new snapshot/evidence, independently review again. |
| BLOCKED            | `REQUEST_CHANGES` when a review is returned; final `BLOCKED` for missing external prerequisite, or `NEEDS_DECISION` for approval/scope/identity boundary | Name exactly what stops and what resolves it. Ordinary repairable failure is not an excuse to terminate authorized work early.               |
| ESCALATE           | Non-approval / `REQUEST_CHANGES`; final `NEEDS_DECISION` when owner choice is required                                                                   | Orchestrator presents proposed-ADR brief, records decision and propagation before dependent resumption.                                      |

The checklist's final outcome is READY, CHANGES REQUIRED, BLOCKED or ESCALATE; these labels summarize existing states rather than replace the global templates. READY means implementation handoff readiness, not merged/released. Reviewer Critical maps to the global template's `blocker`; High/Medium/Low retain their meaning. Keep every required FAIL/NOT VERIFIED criterion visible.

Count completed independent review passes from the same PR history, including resumes: default maximum **three**. Fix comments, debugging and ordinary test attempts do not consume a review pass. Finish on the first current independent approval with required checks passing; after three unsuccessful passes stop NEEDS_DECISION. No fourth pass or reset on contract revision without explicit owner budget. Preserve historical contracts/findings and exact current frozen version.

Before final handoff refresh head/base, checks, mergeability and posted review. Base advancement needs compatibility verification; implementation changes need a new review. Preserve the user's milestone-specific unchecked Manual Checkpoint without moving missing required tests into it. Keep the active contract while the PR is open; do not archive, merge, enable auto-merge, delete branches or start dependent milestones automatically.
