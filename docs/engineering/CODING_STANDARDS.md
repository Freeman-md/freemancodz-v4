## Application notes and justified limits

Naming and imports follow actual shapes: `PublicPortfolioService`, `RateLimitRepository`, `createChatPostHandler`, `decodeEvent`, `useAssistant`, `workflowApprovalSchema` and `MAX_MESSAGE_LENGTH`. Generic trusted values can stay camelCase constants; SCREAMING_SNAKE_CASE is not a mutability rule. Existing dotted responsibility suffixes such as `.contract.ts`, `.types.ts` and `.test.ts` remain valid; there is no naming-only migration. The proposed symbol-name rules do not rename framework-required exports or generated/vendor symbols.

For STD-006, a consistent reading order is directives/server-only marker, packages, cross-area `@/` imports, then nearby relative imports, but no automatic alphabetic sort or regrouping is mandated. A side-effect import's semantics take precedence over visual grouping. Named exports are the existing general pattern; default exports required by Next or configuration remain appropriate. Public interfaces/types are optional: `ContactService` uses a `Pick` seam, and `AssistantComposer` uses inline props. No new barrel, shared DTO package or universal interface rule is introduced.

STD-009 deliberately proposes **no new numeric cap** for function length, file length, nesting, cyclomatic complexity or coverage. No repository defect baseline justifies one, and cohesive state machines/transaction code can be made harder to understand by arbitrary splitting. Review instead names the combined responsibilities, difficult branch/failure path or testing obstacle and checks whether a focused extraction improves it. A future numerical gate needs measured evidence, a precise counting/exclusion policy and approval; the catalogue's unrelated 80-line/complexity-12 examples are not imported. The existing Prettier target (100 columns), two-space indentation and required braces are concrete current conventions with deterministic tools. Runtime limits such as message length, leases and batch sizes remain product/reliability contracts, not coding-style thresholds to change here.

STD-011 does not assert that TypeScript validates network data, or prohibit every justified assertion. For example, a narrowed object-key assertion can be reviewed locally; casting arbitrary JSON into a trusted review cannot. `strict: true` is configured, while `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes` are not explicitly enabled; this task adds neither. There is no inspected explicit `no-explicit-any`, consistent-type-imports or floating-promises rule in repository configuration. Proposed restrictions therefore need independent review until an approved deterministic check exists.

STD-014 requires evidence for changed interactions, not an unsupported claim of site-wide accessibility certification. Inspected patterns include the label/IME-aware keyboard handler in `src/app/_assistant/components/AssistantComposer.tsx`, status messages in `AssistantWorkflowConfirmation.tsx`, and focus handling in `src/app/_assistant/hooks/useAssistantSurface.ts`. Browser keyboard/focus/error behaviour remains unexecuted in the audit; default lint cannot establish it. Tests should target the changed behaviour without replacing useful existing primitives or adding a UI subsystem.

STD-015/016 preserve existing deliberate error boundaries. `src/app/_assistant/api/stream-assistant-response.ts` validates every event, reports interruption and releases its reader; cancelling an already failed reader may have a narrowly acceptable cleanup fallback. That is different from swallowing a failed business write. `PublicPortfolioService.read` translates persistence failure into an explicit configuration error; `createChatPostHandler` returns safe HTTP failures. These observations do not approve the app's direct environment reads or certify every logging/async path.
