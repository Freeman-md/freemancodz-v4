## Dependency contract

```text
server app adapters / entrypoints -> modules/composition -> modules + infrastructure
browser app UI -> colocated browser API + contracts + app UI primitives
modules -> own code + contracts + deliberately exposed types / injected operations
infrastructure -> technical dependencies + central configuration

ACCEPTED D2 additions: modules -> type-only technical ports;
                      modules -> explicitly bounded inert public error contracts
```

“Public” means an intentionally documented boundary with a limited responsibility, not every exported symbol. Alias and relative imports have identical architectural meaning. App adapters can import schemas, types and pure transport helpers; composition supplies concrete stateful dependencies to business modules, app adapters and entrypoints. Infrastructure may configure and construct its own vendor/database clients through technical factories, which composition consumes. Infrastructure can use generated database types; that does not authorise module orchestration.

Deliberately public type-only cross-module use is valid without a runtime dependency. Injected runtime operations may use structural inference or `Pick` of an existing public type; they do not require a new named/exported interface. For example, a consumer may import `MeetingSlot` as a type alone, while an operation can receive `Pick<MeetingAvailability, "isSlotAvailable">`. The accepted inert error-value allowance is separate from both.

### D2: exact accepted technical/public error boundary

Type-only injected contracts may remain in their technical owner, for example `OpenAITransport`/request types in `src/infrastructure/openai/types.ts`, `CalendarClient` in `src/infrastructure/google-calendar/types.ts`, and `Logger` from `src/infrastructure/logging/logger.ts`. This avoids duplicate interfaces or a new ports layer. Business modules other than composition, app adapters and entrypoints gain no permission to construct/import concrete clients. Infrastructure-internal vendor configuration/factories remain legitimate: `createOpenAIClient` in `src/infrastructure/openai/client.ts` and `createPrismaClient` in `src/infrastructure/database/prisma.ts` construct technical clients; composition assembles them with modules. Generated Prisma transaction/JSON types can support server persistence contracts without becoming browser models.

The accepted runtime allowance is narrower: a deliberately exposed, side-effect-free error class with bounded codes/outcomes in a file containing no client implementation, environment access, I/O, provider SDK runtime imports or business execution. Type-only imports are erased; the runtime dependency graph still needs inspection. An error's `cause` can be sensitive and is not a safe log/response value.

Candidate symbols covered by the accepted rule are `CalendarAvailabilityError` and `CalendarEventError` in `src/infrastructure/google-calendar/types.ts`, and `MeetingBookingError` in `src/modules/meeting/types.ts`. No other current runtime import is grandfathered. Additional symbols need the same public-boundary review against the accepted rule; changing the boundary itself requires a revised ADR. Approval authorises the stated rule prospectively; existing candidate edges still need compliance classification and evidence in Task07.

`ResendClientError` imported from `src/infrastructure/resend/client.ts` does **not** meet this contract because the file implements the client. Splitting that inert error contract into its existing technical owner, with no extra wrapper, is a possible later remediation; no code relocation is authorised by this approval-propagation task. Direct imports of `MEETING_CONFIG`, `getLondonDate`, `resolveMeetingTime`, `assertMatchingCalendarEvent` or `assertMatchingMeeting` remain outside the allowed cross-module boundary.

## Representative execution flows and consistency

These are source-backed flow specifications preserving existing caller behaviour, not claims of live operation. Public boundary placement and dependency rules above apply throughout.

1. **Published read:** `src/app/page.tsx` / `src/app/work/[slug]/page.tsx` → configured `publicPortfolioService` → `PublicPortfolioService` → published repository → PostgreSQL → serialisable rendered UI. Static generation deliberately restricts case-study slugs. Seed writes and indexing are explicit maintenance workflows; request reads do not implicitly seed or call the app's own API.
2. **Assistant:** private UI → `streamAssistant` → `/api/chat` → body/schema/session checks and transactional rate limits → `AssistantService` → injected OpenAI/portfolio/workflow interfaces → validated stream events. Browser session establishment can return 428; availability/rate-limit failure is explicit. Conversation state is local, saved workflow state is server-owned. OpenAI continuation/storage is current behaviour, not an established privacy/retention policy.
3. **Approval/write:** definition tools edit revisioned draft → persisted review → browser sends review ID and expected revision → `/api/workflow/approve` validates same origin and browser ownership → `WorkflowService.acceptReview` validates definition/version/payload → repository creates durable run → bounded runner pass. Approval/discard is separate from conversation text.
4. **Durable effect:** runner claims due persisted step with token/lease → Meeting action reserves slot → stable Calendar operation → fenced checkpoint/booking confirmation → separately recoverable owner notice. Unknown provider outcome enters reconciliation; stale claims cannot settle new claims. Current limits are a 20-second run signal, batch four, 45-second lease and bounded retries; these values are source observations, not new capacity requirements.
5. **Recovery:** authenticated `/api/internal/workflow-runner` calls the same configured runner. Source/manual scheduler instructions exist; installed scheduling, alerts, provider results and recovery latency are unverified. No release gate passes from this flow diagram.

Repositories own transactions for invariants, not HTTP handlers or composition. Workflow approval atomically links review/run identity; draft edits compare revisions and invalidate pending reviews. Workflow run updates fence claim tokens. Meeting reservation serialises overlap checks; rate-limit counters lock deterministically; portfolio index replacement is transactional. The relevant implementations are `src/modules/workflow/repository.ts`, `run-repository.ts`, `src/modules/meeting/repository.ts`, `src/modules/rate-limit/repository.ts`, and `src/modules/portfolio/repositories/portfolio-search.repository.ts`.

Where one durable transition also changes Meeting reservation state, the owning Workflow transaction passes its transaction handle through the injected persistence operation (`WorkflowRunRepository.checkpoint` and `MeetingReservationStore.release`). This is an explicit atomic collaboration, not permission for an app adapter to manipulate either repository or for workflow code to import the Meeting repository. Provider network effects are outside database transactions and reconcile through durable identities/checkpoints rather than pretending to provide distributed ACID.

The Meeting repository's legacy-workflow overlap read is existing compatibility coupling (`MeetingRepository.reserve`), not permission to spread new cross-module table access. It needs real migration/concurrency evidence and review of any change preserving older pending records. Data/transaction-ownership changes trigger ARC-015.
